### مسار التشغيل الحالي

- **Android:** `MainActivity.gatewayRequest` يطلب الدخول من `sadad-auth`، و`SessionStore`
  يحفظ جلسة الحساب ومغلّف Auth دون قبول رد ناقص. `LedgerQueue` يستخدم هوية ومفتاحًا لكل
  متجر، و`SignedLedgerSync` + `LedgerClient` يسجّلان التركيب ثم يطلبان الترخيص والنسخة
  الموقّعة ويرسلان الطابور. `SadadDatabase.importLedgerView` يعرض النسخة مع العمليات
  المعلقة في الجداول نفسها التي تقرأها الشاشات والتصدير والتذكيرات. تبديل الحسابات يحفظ
  Auth المجدد ويمنع عمل الحساب السابق أو تجاوز قفل الاسترداد.
- **المالية:** الشخص مع أول دين والدفعة الموزعة يُحفظان كاملين داخل معاملة واحدة أو لا
  يُحفظ شيء. المصدر يستخدم الدفتر الموقّع وحده؛ SQLite إصدار 9 يحذف الطابور القديم
  ومشغلاته ويحفظ مالية النسخة المستقلة. كل المتاجر الحالية تجريبية وفق قرار المستخدم.
- **الإدارة:** المصدر الوحيد `server/public/`؛ الحسابات والهوية عبر `sadad-api`، واعتماد
  التركيبات والاسترداد عبر `sadid-ledger`. فحص قائمة الاسترداد قبل الاعتماد، وعرض مالية
  الدفتر والتدقيق باقية. أدوات استعادة snapshot وWhatsApp القديمة حُذفت من المصدر.
- **الإصدار وCI:** فحوص التطبيق واللوحة والوظائف وسلسلة SQL مجتمعة في `android-ci.yml`.
  أصلح الدمج استخدام `runner.temp` غير المسموح داخل `jobs.release.env`: يُضبط مسار
  مفتاح التوقيع من `RUNNER_TEMP` في خطوة على runner عبر `GITHUB_ENV`.
  `HardwareLedgerInstrumentation` صار يستعمل مفاتيح المتاجر والعقد الحالي دون `ledgerMode`.
- **الجلسات الجديدة:** اقرأ هذا القسم مع `AGENTS.md` وابدأ من `main` المحدّث. نسخة worktree
  أو جلسة قديمة تبقى على التزامها حتى تحديثها؛ ليس وجودها دليلًا على أن عمل الفروع ناقص.

### حدود النشر والعمل الباقي

1. اختبار الهاتف المعزول لـ SQLite/Keystore ثم المزامنة المصادق عليها والاسترداد وتبديل
   A→B→A ما زال مطلوبًا؛ بناء instrumentation وحده لا يثبت نجاحه. عطل الواجهة المسجل
   عند `Person ledger operator` لم يُحسم في الدمج.
   ابنِ على هاتف QA بمعرّف منفصل، ثم ثبّت وشغّل:

   ```sh
   ./gradlew assembleServerDebug assembleServerDebugAndroidTest \
     -PSADAD_APPLICATION_ID=com.sadad.qa.correctness \
     -PSADAD_TEST_RUNNER=com.sadad.app.LedgerCorrectnessInstrumentation
   adb install -r app/build/outputs/apk/server/debug/app-server-debug.apk
   adb install -r app/build/outputs/apk/androidTest/server/debug/app-server-debug-androidTest.apk
   adb shell am instrument -w com.sadad.qa.correctness.test/com.sadad.app.LedgerCorrectnessInstrumentation
   ```

   `HardwareLedgerInstrumentation` يتطلب `com.sadad.qa` بالضبط؛ غيّر خصائص البناء والrunner
   معًا عند تشغيله. لا تثبّت QA فوق نسخة تحمل بيانات المستخدم.
2. آخر جرد سحابي، **12 أكتوبر وليس فحصًا جديدًا اليوم**: API v6، Auth v4، ledger v7.
   الدمج والدفع إلى Git لا ينشران وظائف Supabase ولا يطبّقان SQL. Auth مطابق وفق الجرد
   السابق؛ نشره غير مطلوب لمجرد الدمج.
3. بعد مراجعة حزمة النشر واعتمادها: ترحيل النشاط
   `20261012153055_sadid_v3_activity.sql`، ثم ledger، ثم API المنظف واللوحة؛ راجع
   [رقعة ledger](../delivery/reviews/2026-10-12-sadid-ledger-deploy.patch) و
   [رقعة API](../delivery/reviews/2026-10-12-sadad-api-deploy.patch). الدفع إلى `main`
   يشغّل نشر Pages تلقائيًا؛ لا يُعد نجاح الصفحة إثباتًا لنشر backend الجديد.
4. **حذف القديم أخيرًا فقط**: راجع `20261012174647_retire_test_legacy_ledger.sql` بعد نشر
   API الجديد ونجاح QA. خذ نسخة استرجاع خارج المستودع؛ حذف الجداول الآن يكسر API v6.
   سجل الترحيلات السحابي هو المرجع؛ لا تطبّق جميع الملفات المحلية آليًا.
5. APK 2.5.11 في `delivery/apk/` و[حزمة الفريق 2.5.12](https://github.com/Abdalrahman-py/sadad/releases/tag/team-2.5.12-20261012)
   يسبقان إصلاحات الدفتر المدمجة. حزمة الفريق موقعة بشهادة Android Debug، والإصدار الرسمي
   يحتاج مفتاح الإنتاج وأسراره الأربعة وبناءً واختبارًا جديدين. لم يُدفع وسم إصدار من الدمج.

## تحقّق حيّ من المسار القديم ومِن حارس v3 (11 أكتوبر 2026)

  (`GET /mobile/snapshot`) ← رفع دفعة (`POST /mobile/sync-delta`) ← تنزيل بصفحات

- حارس v3 على المتجر 7: `GET /mobile/session` و`POST /mobile/change-password` و
  `POST /mobile/logout` تعمل (`200`)، وبقية مسارات `/mobile/*` تعيد
  `409 legacy_ledger_read_only` بنفس الجملة المتوقعة حرفيًا.
- **عميل التطبيق نفسه**: `LedgerSync` و`HttpSyncTransport` من `app/` تُرجمت كما هي وشُغّلت مقابل
  الخادم الحيّ (الجلسة والدفتر وحدهما بديلان لأنهما يحتاجان Android): 11/11 فحصًا ناجحًا.
  الدفعة التي رفعها العميل وصلت فعلًا إلى الخادم — الصف `id=3` ظاهر في `snapshot-page` — ومتجر
  v3 عاد `BLOCKED` بجملة الخادم نفسها، وجلسة باطلة عادت `UNAUTHORIZED` لا فشلًا صامتًا.

هذا التحقّق جرى على الإصدار **المنشور 6**. أما التنظيف المعماري في `handler.ts` فلم يُنشر بعد.

### الدفتر المعتمد (v3): تحقّق حيّ كامل بلا هاتف (11 أكتوبر 2026)

الاعتقاد السابق أن التحقق من v3 يحتاج هاتفًا غير دقيق. ما يحتاج الهاتف هو **جانب التطبيق**
(مفتاح Keystore وواجهاته)، أما **عقد الخادم** فيمكن التحقق منه من أي جهاز: مفتاح P-256 يُولَّد
برمجيًا، ويُسجَّل بانتباه إلى النص القياسي في `sadid-ledger/proof.ts` (`sadid-v3\nMETHOD\nroute\n
sha256(raw)\ntime\nnonce\ninstallation`، توقيع 64 بايت `r||s` بصيغة base64url).

نُفّذ على المتجر 7 بالتسلسل الكامل:

| الخطوة | المسار | النتيجة |
| --- | --- | --- |
| 1 | `POST /mobile/v3/enroll` | `200` — `status: pending`، `generation: 1` |
| 2 | `POST /admin/installations/approve` | `200` — `status: active` |
| 3 | `GET /mobile/v3/snapshot` | `200` — `epoch` و`cursor` و11 مفتاحًا |
| 4 | `POST /mobile/v3/lease` | `200` — ترخيص موقّع صالح 7 أيام |
| 5 | `POST /mobile/v3/operations` (`contact.create`) | `200` — `status: accepted` مع `operationId` و`entityId` و`sequence: 1` |
| 6 | `POST /mobile/v3/outcomes` | `200` — الإيصال نفسه |

ودخول البوابة `sadad-auth/mobile/login` يعيد `auth.accessToken` و`auth.refreshToken` كما هو متوقع،
وهما ما تحتاجه المسارات الموقّعة (مع `X-Sadad-Session`).

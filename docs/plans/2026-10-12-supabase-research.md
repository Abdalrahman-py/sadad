# بحث مستقل: شروط استكمال الانتقال إلى دفتر Supabase

تاريخ التحقق: 12 أكتوبر 2026. المصدر المحلي: الالتزام `fe79c22fc752b3b24ecc000d66a1f29b85b4a605` في نسخة العمل الحالية. هذه مراجعة للخطة الخارجية `2026-10-12_172453-sadad-supabase-only.md`؛ لم تُعدّل أي وظيفة أو ترحيل، ولم يُكتب شيء إلى الإنتاج.

## القرار

إصلاح سلامة الإدخالات وهوية الحساب والتركيب أولًا، ثم سجل النشاط، ثم حذف العملاء والمسارات التي ثبت انتهاء استخدامها. لا تصلح المرحلة C كما كُتبت للتنفيذ: تضم دالة ما زال الدخول والإدارة يستخدمانها، وتزيل حاجزًا يحمي المتاجر المعتمدة من مسارات واتساب القديمة. إبقاء البروتوكول القديم مؤقتًا قرار تقني مقصود حتى اكتمال نقل جميع المستهلكين؛ وجوده داخل Supabase لا يعني وجود خادم ثانٍ.

## سجل النشاط: ما يصح في الاقتراح وما يحتاج تعديلًا

الحقول المذكورة صحيحة في إنشاء `public.sadid_events` (`20261010100605_sadid_v3_authorization_and_ledger.sql:94-99`). يكتب apply العمليات المقبولة والمرفوضة، حيث تتحول المرفوضة إلى `operation.rejected` (`:290-293`). لذلك يمكن بناء سجل عمليات متجر منه، لكنه لا يحل تلقائيًا محل تاريخ الدخول والخروج أو إجراءات الإدارة في `audit_events` و`control_events`. يجب تسمية الشاشة وعرض أنواع العمليات العربية والمستخدم/الجهاز وفق عقد واضح، وتجنب عرض JSON الأمر أو رموز النوع التقنية للمستخدم.

يصح استعمال قدرة `read` دون توسيع قيود scopes (`:33`). الوظيفة Edge تتحقق من المستخدم بـ`getUser`، ثم مفتاح التركيب، ثم توقيع يربط الطريقة والمسار والمحتوى والوقت والـnonce؛ تصدر قدرة وتقيم RPC بعميل JWT المستخدم (`sadid-ledger/index.ts:42-77`، `proof.ts:4-17`). يجب أن تحافظ الإضافة على هذه السلسلة وعلى حقوق التنفيذ المقيدة. ردود `read` تستعمل حاليًا المفتاح `snapshot` (`index.ts:77`)، لذا قراءة مصفوفة النشاط منه ممكنة، لكن غياب المصفوفة أو تشوهها لا ينبغي تحويله إلى نجاح فارغ في العميل. اجعل ترتيب آخر 200 عملية بالـsequence ثابتًا، أو وفر pagination إذا كانت الشاشة تطلب تاريخًا كاملًا.

اختبار العميل المقترح لا يكفي وحده: اختبر RPC ببيانات اصطناعية لمتجرين، ودور anon/service_role بلا تنفيذ مالي، وقدرة مزورة أو منتهية أو scope خاطئ، وحالة تركيب ملغى، مع نفس سياسات RLS والملكية الموجودة. اختبر الوظيفة Edge والعميل كذلك.

## نتائج الإنتاج التي أعادها المنسق عبر قراءات فقط

المنسق في هذه المراجعة تحقق من نسخ الوظائف وسجل الترحيلات والجداول دون أي كتابة: `sadad-api` v6 و`sadad-auth` v4 و`sadid-ledger` v7، مع 22 قيد ترحيل. حزمة ledger المنشورة تضم index/proof/deno ولا تضم admin.ts أو activity. لذلك نشر الشجرة الحالية يضيف سطح الإدارة أيضًا؛ ليس نشر مسار النشاط وحده. يلزم مراجعة الفرق الكامل وحقوق الوصول وخيار verify_jwt.

الجرد الحي أحدث من الخطة: خمسة متاجر؛ 2 و3 و7 لها دفتر معتمد، والمتجر 6 (`900001`) بلا دفتر معتمد ولديه 4 أشخاص ودين واحد ودفعة واحدة؛ والمتجر 8 (`10101`) بلا دفتر معتمد وجداوله القديمة فارغة. لا يصح اتخاذ قرار التقاعد اعتمادًا على أربعة متاجر أو خمس صفوف. احتفظ بالمسارات إلى أن يكتمل قرار ونقل الحسابين غير المعتمدين، مع جرد العملاء/الأجهزة الفعلية، دون حذف بياناتهم بناءً على وصفها بأنها تجريبية.

هذه النتائج قرأها المنسق، ولم يُعِد كاتب هذا البحث تنفيذ الاستعلامات أو جلب صفوف العملاء. الأرقام لا تثبت عدم وجود عميل قديم آخر في الأجهزة الميدانية.

## أخطاء تحقق في الخطة

- `sadad-api/handler.ts:935-936` يستدعي requireSession قبل اختيار معظم مسارات mobile. لذلك طلب sync بلا اعتماد يمكن أن يجيب 401 بعد حذف المسار، لا 404. اختبر حذفه بجلسة QA صالحة، واقرأ الحزمة المنشورة للمقارنة.
- في ledger يُفحص JWT قبل التعرف على snapshot/activity (`index.ts:42-64`). إجابة 401 بلا اعتماد تثبت رفض الاتصال فقط، ولا تثبت وجود route أو RPC. يحتاج التحقق الناجح JWT وتركيبًا معتمدًا وتوقيعًا صالحًا، ثم فحص schema/قيد المتجر؛ فشل RPC غير المنشور قد يظهر 503 بحسب catch (`:79-80`).
- SQL النشاط يجب أن يصل قبل الوظيفة التي تستدعيه، ثم العميل؛ إزالة activity القديم خطوة لاحقة لتوافر البديل. قيّد db push بالترحيلات التي تمت مراجعتها، ولا تشغّل كل pending migration دون مقارنة بسجل الإنتاج.
- `sadad-auth/handler.ts:212-235` يبقي فحص تعليق المتجر وتطابقه وكلمة المرور؛ لا يوجد دليل يجعله غير قابل للوصول بعد إزالة بروتوكول الدفتر. لا تقلصه لمجرد انخفاض عدد المسارات.
- `sadad_sync_identity_sequences` و`sadad_admin_overview` لا يظهر لهما caller في كود الوظائف الحالي، لكن ذلك وحده لا يثبت عدم استعمالهما من أداة خارج المستودع. ليس حذفهما أولوية إصلاح المستخدم.

## التحقق المنفذ في هذه المراجعة

على Deno `2.7.12`، نجحت `deno check --frozen index.ts` و`deno test --frozen -A` في كل مجلد: sadid-ledger **3**، sadad-api **22**، sadad-auth **11**؛ المجموع **36 اختبارًا ناجحًا، بلا فشل**. لا تعني هذه النتيجة وجود تغطية للثغرات أعلاه أو تحققًا من RPC جديدة. لم تُشغل اختبارات جهاز أو ترحيل جديد ضمن هذا البحث.

## مصادر الوثائق الرسمية ونتيجة البحث

حُل معرف Context7 أولًا إلى `/supabase/supabase` ثم استُخدمت استعلامات منفصلة للتفويض والوظائف وصيانة الترحيلات. قُرئت الصفحات الرسمية مباشرة للتحقق الإضافي. محاولة Jina عبر agent-reach لم تعمل بسبب DNS في البيئة؛ استُعمل web الرسمي كبديل. لم تُجرَ ترقية أو إعادة تهيئة أدوات.

- [Supabase: ترويسات تفويض Edge](https://supabase.com/docs/guides/functions/auth-headers): `Authorization` لرمز المستخدم و`apikey` لمفتاح المشروع. طبقة verify_jwt تعمل قبل handler، وقبول مفتاح API وحده لا يثبت مستخدمًا. الاستنتاج: احفظ التفويض الداخلي ولا تستخدم رمز 401 كإثبات لمسار؛ ثبّت إعداد النشر الفعلي لكل وظيفة قبل تغييره.
- [Supabase: وظائف قاعدة البيانات](https://supabase.com/docs/guides/database/functions): invoker الافتراضي، خطر صلاحيات definer، search_path فارغ، وضرورة تقييد execute. الاستنتاج: الاقتراح يتبع نمط الملكية/المنح المحلي الصحيح، لكن يجب نسخه من النسخة المقواة واختبار الدور الفعلي وRLS.
- [Supabase: سير عمل CLI](https://supabase.com/docs/guides/local-development/cli-workflows): مقارنة migration list، سجل `supabase_migrations.schema_migrations`، ومعاينة db push بـdry-run. الاستنتاج: راجع الفرق الفعلي بين المحلي والمنشور قبل أي migration أو deploy؛ لا يعد dry-run اختبارًا لتنفيذ SQL.
- [Supabase: إعداد الوظائف](https://supabase.com/docs/guides/functions/function-configuration): إعدادات verify_jwt منفصلة لكل وظيفة. `config.toml` المحلي يحدد api/auth فقط؛ دوّن إعداد ledger المنشور ولا تستنتجه من غياب القسم.
- [Supabase: تقاعد بعض TLS 1.2 CBC](https://supabase.com/changelog/cbc-tls-ciphers-deprecated)، إعلان 12 أكتوبر 2026، موعد إزالة يبدأ في 10 نوفمبر 2026: يشمل HTTP API وAuth وEdge. متابعة ثانوية: تحقق من الاتصال على أقدم جهاز مدعوم؛ لم يثبت هذا البحث تأثر جهاز بعينه، وليس سببًا لتأخير إصلاحات البيانات.
- [Supabase: ترقية PostgreSQL 15.19/17.11](https://supabase.com/changelog/postgres-15-19-17-11-breaking-changes): أثر مشروط باستعمال ltree أو PGP legacy أو btree_gist float أو custom operators. لا يظهر ذلك في المسارات المالية التي تتبعها هذا البحث؛ لم تُفحص جميع extensions المنشورة.

## الترتيب المقترح للعمل الخلفي

1. تثبيت baseline الشجرة والمنشور، وحصر فروق حزمة ledger كاملةً، مع المحافظة على بيانات وأوامر الحسابات.
2. إصلاح هوية التركيب/التفويض المحلي مع إصلاحات صحة المدفوعات والمزامنة التي سجلتها مراجعة التطبيق، قبل أي إزالة واجهة قديمة.
3. اختبار سلسلة الترحيلات الحالية عبر harness حقيقي، وتوصيله بـCI للمسارات SQL/scripts.
4. بناء RPC النشاط بعد مراجعة أحدث التقوية، اختبارها محليًا مع Edge، ثم تقديم migration + فرق الوظيفة الكامل للمراجعة. نشر SQL ثم ledger ثم إصدار التطبيق حين يُصرّح بالنشر.
5. إصلاح بقية مستهلكي البيانات القديمة: الدخول، الإدارة، وواتساب أو إبقاء رفض v3 لها. إبقاء makeSnapshot والحواجز ما دام لها مستهلك مثبت.
6. نقل/تسوية المتجرين غير المعتمدين والتحقق من أجهزة الميدان قبل إزالة sync/sync-delta/snapshot/snapshot-page. اختبار الدخول والإدارة والخروج وواتساب بعد كل حذف.
7. توثيق النتائج المقاسة وحدود تحقق الجهاز، ثم تنظيف أدوات المعاينة والتوثيق؛ حذف الأدوات وعدد الأسطر ليسا معيار نجاح مالي.
